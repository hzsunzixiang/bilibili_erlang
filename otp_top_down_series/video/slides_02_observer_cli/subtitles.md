# Erlang observer_cli — 没有 GUI 时，继续观察同一个 BEAM 运行时

> 与 `presentation.tex` 逐页对应
> 目标受众：Erlang 和 OTP 初学者
> 时长目标：6-10分钟

## 第1页：封面

**标题**：Erlang observer cli
**副标题**：没有图形界面时，继续观察同一个 BEAM 运行时

**演讲稿**：
大家好，这一集我们继续讲 Observer，不过这次换成终端里的 observer cli。它和图形界面观察的是同一个 BEAM 运行时。不同的是，图形界面更适合看结构，终端工具更适合在线上快速排查指标。

---

## 第2页：两种观察方式：可视化 vs 终端

**标题**：两种观察方式：可视化 vs 终端

**演讲稿**：
上一集我们已经建立了一个直觉：Erlang 的关键运行时对象是 Process。它有邮箱、状态、内存和调用现场。这一集不换主题，只是把观察入口从图形界面换到终端。

---

## 第3页：Observer UI 和 observer cli 的关系

**标题**：Observer UI 和 observer cli 的关系

**演讲稿**：
Observer UI 和 observer cli 不是替代关系，而是两种入口。图形界面适合教学和理解 OTP 结构，尤其是 application 和 supervisor tree。终端界面适合服务器、容器和远程环境，重点是按指标快速缩小范围。

---

## 第4页：终端场景下，问题会换一种问法

**标题**：终端场景下，问题会换一种问法

**演讲稿**：
在图形界面里，我们常问系统怎么组织。在终端排查时，我们更常问哪个进程占内存，谁执行最频繁，哪个邮箱正在堆积，哪张表异常增长。所以 CLI 版的主线，是从指标出发找到具体对象。

---

## 第5页：启动 demo：沿用 UI 版的 full otp app

**标题**：启动 demo：沿用 UI 版的 full otp app

**演讲稿**：
这里我们沿用上一集的 demo。好处是，UI 版看到的 application、worker、状态机和表，在 CLI 里仍然是同一批运行时对象。这样你会更容易理解：工具换了，但观察对象没有变。

---

## 第6页：Home：终端版的运行时仪表盘

**标题**：Home：终端版的运行时仪表盘

**演讲稿**：
启动 observer cli 后，Home 页面就像一个终端版运行时仪表盘。这里先看节点级指标，比如进程数量、内存、调度器、运行队列和端口数量。它的作用是先判断整个节点有没有明显异常。

---

## 第7页：Home 页面不是截图目录，而是排查入口

**标题**：Home 页面不是截图目录，而是排查入口

**演讲稿**：
Home 页面不是为了展示所有细节，而是为了决定下一步看哪里。内存异常，可以继续看进程或表；执行压力异常，可以看 reductions；延迟异常，可以看消息队列。终端排查的关键，是先缩小范围。

---

## 第8页：App：从 application 维度看聚合指标

**标题**：App：从 application 维度看聚合指标

**演讲稿**：
App 页面从 application 维度展示聚合指标。它会告诉我们每个 application 的进程数量、内存、执行量和消息队列情况。这里不展开监督树，而是帮助我们判断资源主要花在哪个 application 上。

---

## 第9页：App 页面：答案从结构变成聚合

**标题**：App 页面：答案从结构变成聚合

**演讲稿**：
这一页要对齐 UI 版的理解。图形界面的 Applications 页面回答系统怎么组织，observer cli 的 App 页面回答资源花在哪里。一个偏结构，一个偏指标，但它们都服务于同一条 OTP 主线。

---

## 第10页：命令行里看监督树，仍然直接用 OTP API

**标题**：命令行里看监督树，仍然直接用 OTP API

**演讲稿**：
如果在终端里想看监督树，不一定要强行让 observer cli 做所有事情。OTP 本身提供了标准 API，可以查看 supervisor 的子进程。更清晰的分工是：结构用 OTP API 查，异常用 observer cli 缩小范围。

---

## 第11页：Processes：按指标找到具体 Erlang Process

**标题**：Processes：按指标找到具体 Erlang Process

**演讲稿**：
Processes 页面是终端排查里非常重要的一页。我们可以按内存、执行次数和消息队列排序，先找出最可疑的进程。这里的 process 仍然不是操作系统进程，而是 BEAM 管理的 Erlang Process。

---

## 第12页：从列表进入详情：把指标落回运行现场

**标题**：从列表进入详情：把指标落回运行现场

**演讲稿**：
排序只是入口，真正要确认的还是某个进程的运行现场。内存高，要看它持有什么数据；执行次数高，要看当前函数；消息队列高，要看谁在发消息，以及它为什么处理不过来。

---

## 第13页：ETS：从表维度看运行时数据压力

**标题**：ETS：从表维度看运行时数据压力

**演讲稿**：
ETS 页面从表的维度观察运行时数据压力。它适合看表数量、表名、拥有者进程、内存和对象数量。图形界面适合教学时看表内容，CLI 更适合在服务器终端里看表指标。

---

## 第14页：ETS 不是旁支，它常常是 process 问题的一部分

**标题**：ETS 不是旁支，它常常是 process 问题的一部分

**演讲稿**：
ETS 表通常由某个进程拥有，所以表异常常常要回到 owner process。比如缓存表不断增长，可能是缓存 worker 的业务逻辑问题。排查路径通常是先找到异常表，再回到拥有它的进程。

---

## 第15页：observer cli 背后不是魔法

**标题**：observer cli 背后不是魔法

**演讲稿**：
observer cli 背后不是魔法。它依赖的是 Erlang 和 BEAM 提供的运行时观察能力，比如系统信息、内存信息、进程信息、application 信息和表信息。工具只是把这些能力组织成更方便的终端界面。

---

## 第16页：什么时候用 observer cli？

**标题**：什么时候用 observer cli？

**演讲稿**：
当你通过远程终端连接服务器，或者在容器里排查问题时，observer cli 很有价值。它适合快速看内存、进程、表和系统指标。但如果是第一次理解 supervisor tree，图形界面通常更直观。

---

## 第17页：小结：CLI 版补上的是线上观察能力

**标题**：小结：CLI 版补上的是线上观察能力

**演讲稿**：
这一集的重点是：observer cli 补上了线上观察能力。它观察的仍然是 BEAM 里的 process、application 和 ETS 表。Observer 不是终点，它是理解 OTP 运行结构的入口。下一集开始，我们就回到 OTP 主线，正式讲 application，再逐步展开 gen server 和 gen statem。
